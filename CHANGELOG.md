| connector v1 (doc correction) | 2026-07-20 | **Withdraw an incorrect security claim.** [`docs/MGP_CONNECTOR.md`](docs/MGP_CONNECTOR.md) §3.2 and §6.1 stated that the integrity of the files a v1 `magic_seal` does not cover was "delegated to the lockfile of `install.package_manager` (`uv.lock`, `Cargo.lock`)". A lockfile pins *resolved third-party dependencies*; it does not attest a project's own source files ([uv](https://docs.astral.sh/uv/concepts/projects/layout/) records "the exact resolved versions that are installed in the project environment"; [Cargo](https://doc.rust-lang.org/cargo/faq.html) ensures "the exact same dependencies and versions are used" and warns that "this determinism can give a false sense of security"). The gap is widest under modern packaging: when the entry-file is a thin shim re-exporting an installed package, its hash can stay byte-identical across releases that rewrite the entire implementation — observed in practice across six consecutive releases of one connector, including a full repackage. §6.1 now states plainly that v1 attests the entry-file and nothing else, adds a MUST NOT against presenting a v1 seal as evidence that a distributed tree is unmodified, notes that a catalog-supplied artifact digest is authenticated only by whatever protects the catalog response unless it is bound into the signed message, and adds "bind the artifact digest and length into the signed message" as a v2 candidate alongside the existing Merkle option. Documentation only — no schema, wire-format, or `$id` change, and no new normative requirement on existing implementations beyond the presentation MUST NOT. |
| connector v1 (seal coverage) | 2026-07-20 | **Specify the catalog seal's artifact binding (seal message v2).** [`docs/MGP_CONNECTOR.md`](docs/MGP_CONNECTOR.md) §6.1 promotes the first of its v2 candidates from candidate to specified: a catalog seal MAY sign `archive_sha256` and `archive_length` alongside `connector_id` / `version` / `entry_point_sha256`, under an `mgp-seal/v2` first line that domain-separates it from v1 so a v1 signature can never be replayed as a v2 one. Length is signed with the digest so a consumer can bound a transfer *before* streaming it rather than discovering a mismatch at the final comparison (as TUF does). Four consumer requirements: reconstruct the message version the record actually carries; compare the **signed** digest and length against the downloaded archive before extraction (a signature over a digest nobody checks is not integrity); never treat a digest served elsewhere in the catalog response as authenticated on its own, and read a disagreement between the two as evidence of tampering; treat an unparseable binding as *unverifiable* rather than silently falling back to v1, which would report a legitimate seal as tampered. Records that **downgrade to a pre-v2 v1 seal for the same `(connector_id, version)` remains open** — closing it means re-sealing a corpus under v2 and then refusing v1, which is verifier policy rather than message format, and implementations SHOULD document which they do. §3.2 gains a pointer noting this is a property of the catalog's signed record, not of the `magic_seal` field. Reference implementation `mgp-seal` ≥ 0.4.1 (`canonical_message_v2`, Cloto-dev/mgp-rs). No schema, wire-format, or `$id` change — the connector manifest still binds `magic_seal` to a single entry-file. Per the precedent of the preceding connector-doc rows, the MGP protocol version is not bumped. |

## Migration to mgp-spec repo

Prior to 2026-05-07, the MGP specification was maintained inside [`Cloto-dev/cloto-mcp-servers/docs/`](https://github.com/Cloto-dev/cloto-mcp-servers/tree/main/docs). The specification has been extracted into this independent repository (`Cloto-dev/mgp-spec`) under MIT license, fulfilling the planned "License and Distribution Strategy" described in [MGP_GUIDE.md §17.4](docs/MGP_GUIDE.md#174-license-and-distribution-strategy). The 6 specification documents migrated to this repo retain their original content; the only changes are:

- Child documents (`MGP_SECURITY.md`, `MGP_COMMUNICATION.md`, `MGP_DISCOVERY.md`, `MGP_GUIDE.md`) version header bumped from `v0.6.0-draft, 2026-03-06` to `v0.6.1-draft, 2026-04-22` (sanity-aligned with main `MGP_SPEC.md`)
- Cross-document URLs converted from absolute `cloto-mcp-servers/blob/main/docs/...` paths to relative paths (`MGP_*.md`)

The historical record in `MGP_GUIDE.md §17.10 Roadmap` (which lists `v0.6.0-draft` as the Phase 0 deliverable) is preserved unchanged because it documents the original draft state, not the current spec version.
